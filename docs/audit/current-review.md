## Read-only prior-art checks

The public official reference-solution repository was cloned and its README and notebook inspected. It describes a U-Net/Monte-Carlo patch workflow, reads `data/numeric_features.tif` plus `data/labels.tif`, and writes an example GeoTIFF from the label raster's grid. It is useful as a baseline reference, not as a current data source, holdout evaluator, receipt, or proof that any candidate beats the hidden test.

The public owner-maintained GEMSDOE32 repository was read at a pinned commit to understand the named H33 artifact. Its own audit describes the file as a previously used emission after a catalogue-proximity pruning rule. This supports a plausible metric/placement explanation, not a verified causal explanation of any organizer score.

The public owner-maintained `GEMSDOE` root template was inspected at commit `dcbbb192e56b2b32c0a131eba791dc363305d4a3`. Its `data/bridge` contains five feature shards plus the label and sample rasters. Every shard digest/length, the concatenated 418,912,844-byte feature TIFF, and both other full TIFFs match the bridge manifest; all three reconstructed file hashes also match the committed `data/evidence/inventory.json` generated by the owner's GitHub-hosted runner. The temporary copies passed GEMSDOE54's structural input audit: aligned EPSG:32611 grids, 19 nonconstant bands, binary labels, and 60,988 total positive label pixels. This is a `DATA-AUDIT`, not HOLDOUT-DTI. The owner bridge says it originates from the official data-tab Dropbox mirrors, but neither the bridge nor its hashes authenticate organizer origin. The files remained outside this checkout and were not used for a candidate.

The same template exposes `scripts/block_holdout_eval.py`, `src/blocks.py`, `configs/config_block_holdout.yaml`, `.github/workflows/block-holdout.yml`, and `src/submission_io.py`. The holdout trains over four folds of 512-pixel spatial blocks with a 3-pixel boundary collar; it does not use whole fault-segment components as the held-out unit required here. The evaluator name is not `evaluate_holdout.py`, and the writer is `src/submission_io.py`, not `submission_writer.py`. No private replacement was made and no compliant holdout result was generated. The full byte, grid, and protocol findings are recorded in [`pinned-template-cache-audit.json`](pinned-template-cache-audit.json).

Separately, the public owner-maintained GEMSDOE52 repository was used only as a read-only cache integrity test. Its tracked raster bytes do not match its own manifest pins, and all checked-in feature bands are constant on the valid footprint. Its manifest states that the pins are owner-supplied and not organizer-authenticated. The audit is retained at [`sibling-cache-audit.json`](sibling-cache-audit.json); it remains rejected.

## Result

No score-ready TIF was generated. This is deliberate: an owner-pinned input mirror is not organizer-authenticated, and the inspected shared evaluator does not implement the required whole-fault-segment holdout. A format-valid file would not be a scientifically validated submission. The visible site status therefore says **no file is available; do not upload**.

The run-card decision is negative. The local power tool and raster validator are safeguards for a future compliant shared evaluation path; they do not replace that path. The required withheld-positive count, independent-unit count, paired variance, raw DTI detection floor, cluster-bootstrap 95% interval, feature-only AUC canaries, and registry uniqueness comparison are all unmeasured here. The hash-matched cache's total label-positive count is recorded separately as a data-audit property only.
